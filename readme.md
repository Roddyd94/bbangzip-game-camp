# 02주차 — 볼링 게임 — 프레임별 점수 계산

## 1. 이번 주차의 주제

투구할 수 있는 볼링 씬에서 점수와 프레임 진행 시스템을 완성합니다. 공·핀의 물리와 조작은 제공하며, 구현한 규칙이 점수판과 다음 투구 준비에 반영됩니다.

### 훈련 상황

공을 던지고 핀을 쓰러뜨리는 플레이 장면이 제공된다는 전제에서, 경기 규칙 담당으로 점수와 프레임 진행을 붙이는 상황입니다. 제공 시스템이 전달하는 투구 결과를 받아 유효성을 검사하고 스트라이크·스페어·마지막 프레임을 계산해 점수판과 다음 투구 준비에 연결하는 훈련입니다. 물리 결과와 경기 규칙을 분리하고, 같은 투구 기록으로 계산을 재현하는 경험을 목표로 합니다.

## 2. 사전 지식

아래 개념·검색어를 따라 개인적으로 학습하고, 확인 질문에 작은 계산·그림·코드로 답할 수 있는지 살펴봅니다. 학습 노트 제출은 필요하지 않습니다. 설계 패턴은 이해를 돕는 수단이며 특정 구조를 강제하지 않습니다.

| 분야 | 학습할 개념·검색어 | 구현과의 연결 | 스스로 확인할 질문 |
|---|---|---|---|
| 수학·물리 | 정수 합산·범위·불변식 | 핀 수는 정수이고 일반 프레임 합은 10 이하입니다. 운동 물리학은 필요하지 않습니다. | 12회 스트라이크는 왜 300점일까요? |
| 컴퓨터 과학 | 상태 전이·경계값·부분 결과 | 프레임과 투구 인덱스를 구분하고 보너스 대기 중인 점수를 모델링합니다. | 10프레임의 추가 투구를 새 프레임으로 세면 어떤 문제가 생길까요? |
| 게임 엔진 원리 | Rigidbody·투구 완료 이벤트·UI 바인딩 | 제공 물리가 확정한 핀 수를 받아 규칙을 계산하고 반환 상태를 UI에 반영합니다. | 투구 완료를 여러 프레임 통지해도 한 투구로 처리하려면? |
| 알고리즘·자료구조 | List<int>, 순차 순회, 다음 원소 참조 | 스트라이크는 다음 2투구, 스페어는 다음 1투구를 참조합니다. | 아직 다음 투구가 없을 때 범위 밖 접근을 어떻게 막을까요? |
| 설계 패턴 | 단일 책임·순수 계산 함수 | 입력 검증·저장·계산·출력을 분리합니다. 복잡한 State 계층은 필수가 아닙니다. | 같은 투구 목록으로 계산을 반복하려면 어떤 상태 변경을 피해야 할까요? |
| 운영체제 | Unity 메인 스레드·관리 메모리·객체 생명주기 | 씬의 MonoBehaviour와 독립된 C# 규칙 객체의 수명을 구분합니다. 물리 튜닝은 제공 범위입니다. | 씬 재시작 때 이전 투구 기록이나 이벤트 구독이 남지 않게 하려면? |

## 3. 구현 환경 세팅

환경: **Unity / C# / 제공 볼링 씬**.

**제공 상태:** 현재는 문서·`.gitignore`만 있습니다. 아래 Starter Kit 구성·인터페이스·경로는 제공 목표 명세이며 구현된 파일이 아닙니다. 실제 세션은 운영자가 핵심 로직이 비어 있는 실행 가능한 Starter Kit를 배포한 뒤 시작합니다. 참여자에게 주변 시스템 제작을 과제로 넘기지 않습니다.

코어 클래스의 책임 분리는 참여자가 설계합니다. 점수·진행 규칙은 물리 콜백이나 UI에 중복 구현하지 않습니다. 제공 기반은 그 결과를 장면에 반영합니다.

1. 배포된 Starter Kit의 `ProjectSettings/ProjectVersion.txt`에 맞는 Unity 에디터를 Hub에서 설치하고 Windows 빌드 지원 모듈을 추가합니다. 실제 버전·패키지 잠금 파일은 운영자가 배포 시 고정합니다.
2. 5절에 따라 Fork·복제한 저장소 루트를 Hub에 추가합니다. `Assets/`, `Packages/`, `ProjectSettings/`가 있는 폴더가 프로젝트 루트입니다. 빈 프로젝트를 새로 만들지 않습니다.
3. 패키지 복원을 기다린 뒤 제공할 `Assets/Scenes/Bowling.unity`를 열고 Play합니다. 기본 조작·카메라·표시와 디버그 입력이 동작하고, 미완성 코어 때문에 목표 기능만 비어 있는지 확인합니다.
4. 제공 어댑터가 참조하는 `Assets/Scripts/Study/`의 코어와 DTO를 확인합니다. 아래 인터페이스 이름은 설계 예시이며 배포 Kit의 실제 선언을 기준으로 구현합니다. Rigidbody·콜라이더·카메라·UI를 다시 만들지 않습니다.

Unity의 정확한 에디터·패키지 버전과 실제 조작키는 프로젝트 배포 시 이 절에 기록합니다. 현재 특정 버전을 임의로 설치하거나 프로젝트를 생성할 필요는 없습니다.

## 4. 기획안과 구현 목표

### 제공 코드와 핵심 코드의 연결

다음은 Starter Kit가 충족해야 할 계약입니다. 화면·물리·입력 제공 코드가 핵심 정답을 대신 구현하지 않도록 구분합니다.

- 제공 어댑터가 한 투구 종료마다 `RollResult(rollId, knockedPins)`를 한 번 전달합니다. `knockedPins`는 이번 투구에서 새로 쓰러진 핀 수이며 누적 수가 아닙니다.
- 참여자 규칙 코어는 기록을 검증하고 `BowlingState`를 반환합니다. 현재 프레임·다음 투구 번호·확정/미확정 프레임 점수·총점·종료 여부와 `KeepRemainingPins / ResetFullRack / FinishGame` 진행 지시를 포함합니다.
- 제공 핀 관리자는 지시에 따라 핀을 유지하거나 다시 세우고, UI는 반환한 점수를 표시합니다. 핀 관리자나 UI에 점수·프레임 판단을 중복 구현하지 않습니다.
- 이미 처리한 rollId의 중복 전달은 추가 투구로 세지 않으며, 이전 진행 지시를 장면에 다시 실행하지 않습니다. 같은 ID에 다른 핀 수를 보내도 새 투구로 인정하지 않습니다. 잘못된 결과는 기록·점수·진행 상태를 바꾸지 않고 거부합니다. 장면 어댑터의 기본 중복 방지와 별개로 코어의 중복 처리를 확인합니다.
- 실제 물리만으로 300점을 재현하기 어려우므로 제공 디버그 도구에서 핀 수·rollId를 지정해 동일한 코어를 호출합니다. 핀 수를 강제로 주입할 때도 물리 계산기를 따로 만들지 않습니다.

### 기획 규칙과 범위

- 투구당 0~10핀입니다. 1~9프레임은 최대 2회 투구하되 스트라이크면 다음 프레임으로 넘어갑니다.
- 스트라이크는 다음 2회 투구, 스페어는 다음 1회 투구를 보너스로 더합니다. 보너스 투구가 남은 프레임은 점수 미확정으로 표시해도 됩니다.
- 10프레임은 스트라이크면 2회, 스페어면 1회 추가 투구합니다. 추가 투구는 새 프레임을 만들지 않습니다.
- 점수 미확정과 0점을 구분합니다. 보너스가 부족하면 해당 프레임 점수와 그 이후의 누적 점수는 미확정으로 표시합니다. 총점은 처음부터 연속으로 확정된 프레임까지의 합이며, 모든 투구 종료 시 최종 점수가 됩니다.
- 10프레임이 일반 프레임으로 끝나면 추가 투구 없이 종료합니다. 10프레임 자체에는 별도의 미래 프레임 보너스를 계산하지 않고 허용된 2~3회 투구를 합산합니다.
- 10프레임 첫 투구가 스트라이크인 경우 핀을 다시 세웁니다. 둘째도 스트라이크면 다시 세우고, 아니면 셋째는 둘째 투구 후 남은 핀 범위입니다.

- 일반 프레임 첫 투구가 스트라이크면 ResetFullRack, 아니면 KeepRemainingPins입니다. 둘째 투구 후에는 다음 프레임을 위해 ResetFullRack입니다.
- 10프레임에서 스페어를 만들면 추가 투구 전 ResetFullRack입니다. 마지막 허용 투구 후에는 FinishGame만 반환합니다.
- 새 게임은 투구 기록·프레임·점수·완료 상태와 처리한 rollId 목록을 초기화합니다. 제공 어댑터는 이전 경기의 지연 콜백을 폐기하고 진행 중인 물리 투구를 정리합니다.
- 한 경기·한 플레이어·핀 10개·프레임 10개를 기본으로 합니다. 파울은 제공 측이 0핀 결과로 변환하며 핸디캡·멀티플레이는 이번 범위에 포함하지 않습니다.

**선택 확장:** 자동화 단위 테스트, 여러 경기 기록. 프레임별 UI 틀은 제공하고 표시할 점수는 참여자가 계산합니다.
**참여자 구현에서 제외:** 공·핀 물리, 레인 렌더링, 투구 조작·카메라·UI 배치. 이 요소들은 Starter Kit가 제공합니다.

### 구현할 기능

1. 제공 투구 결과를 받아 유효한 기록만 추가하고 중복 결과를 다시 세지 않습니다.
2. 10프레임 점수와 스트라이크·스페어 보너스를 계산하고 미확정 점수를 구분합니다.
3. 현재 프레임·투구와 다음 핀 준비 지시를 반환해 실제 장면 진행에 연결합니다.
4. 10프레임 추가 투구·게임 종료·새 게임 초기화를 처리합니다.

## 5. 프로젝트 Fork와 세팅 후 빌드

### Fork와 작업 브랜치

1. 운영자가 Starter Kit를 배포한 원본 저장소를 Fork합니다. 현재 문서 전용 상태에서는 빌드할 대상이 없으므로, 프로젝트 제공 뒤 아래 절차를 진행합니다.
2. PowerShell 명령의 `<...>` 전체를 실제 URL로 바꿉니다. 이미 복제했다면 clone·remote add는 반복하지 않습니다.

```powershell
git clone <개인-Fork-URL> bbangzip-game-camp
cd bbangzip-game-camp
git remote add upstream https://github.com/Roddyd94/bbangzip-game-camp.git
git fetch upstream
git switch -c work/02 upstream/week/02-bowling
```

현재 원격에는 main과 01주차만 공개되어 있습니다. **02주차 브랜치가 원격에 배포된 뒤** 위 fetch·switch 명령을 실행합니다. 현재 로컬의 `week/02-bowling`은 운영자가 기반을 준비하는 브랜치입니다.

`git switch -c work/02 upstream/week/02-bowling`은 받아 둔 원본 2주차에서 개인 로컬 작업 브랜치를 만들고 전환합니다. 업로드는 수행하지 않습니다. `origin`은 개인 Fork, `upstream`은 원본입니다. 기존 작업 브랜치에서는 `git switch work/02`을 사용합니다. 이후 3절로 환경을 확인하고 4절의 핵심 코드를 구현합니다.

### 빌드와 실행

1. 제공 에디터 버전으로 저장소 루트를 열고 `Assets/Scenes/Bowling.unity`에서 Play합니다. 제공 씬·스크립트를 그대로 사용하며 비어 있는 핵심 코어를 완성합니다.
2. 배포 에디터의 빌드 설정에서 Windows 대상을 선택하고 제공 씬이 빌드 목록에 포함·활성화되어 있는지 확인합니다.
3. **Build And Run**으로 저장소 루트의 `Builds/Windows/`에 출력합니다. 실행 파일과 함께 생성된 데이터 폴더 등 출력 전체를 유지합니다.
4. 실제 플레이와 제공 디버그 입력 양쪽에서 4절의 목표 동작이 같은 코어를 통해 반영되는지 확인합니다.

`Assets/`의 `.meta`, `Packages/`, `ProjectSettings/`는 함께 관리합니다. `Library/`, `Temp/`, `Builds/`는 `.gitignore`로 제외합니다. 위 씬 경로는 제공 목표이며 현재 파일이 존재한다는 뜻은 아닙니다.

구현 후 변경한 코드·필요한 에셋과 .meta·README를 선택해 커밋하고 `git push -u origin work/02`로 개인 Fork에 올립니다. 공통 진행·공유·발표 방식은 main의 운영 안내를 따릅니다. 별도 보고서 없이 코드·실행 안내, 짧은 시연, 핵심 설명 3~5줄이면 충분합니다.
