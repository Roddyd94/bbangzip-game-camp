# 02주차 — 볼링 게임 — 프레임별 점수 계산

## 1. 이번 주차의 주제

투구 기록을 프레임과 보너스 규칙에 따라 점수로 바꿉니다. 입력의 유효성과 마지막 프레임의 경계 조건을 모델링합니다.

## 2. 사전 지식

아래 개념·검색어를 따라 개인적으로 학습하고, 확인 질문에 작은 계산·그림·코드로 답할 수 있는지 살펴봅니다. 학습 노트 제출은 필요하지 않습니다. 설계 패턴은 이해를 돕는 수단이며 특정 구조를 강제하지 않습니다.

| 분야 | 학습할 개념·검색어 | 구현과의 연결 | 스스로 확인할 질문 |
|---|---|---|---|
| 수학·물리 | 정수 합산·범위·불변식 | 핀 수는 정수이고 일반 프레임 합은 10 이하입니다. 운동 물리학은 필요하지 않습니다. | 12회 스트라이크는 왜 300점일까요? |
| 컴퓨터 과학 | 상태 전이·경계값·부분 결과 | 프레임과 투구 인덱스를 구분하고 보너스 대기 중인 점수를 모델링합니다. | 10프레임의 추가 투구를 새 프레임으로 세면 어떤 문제가 생길까요? |
| 게임 엔진 원리 | 규칙과 입력·UI 분리 | 콘솔을 엔진 UI의 대체물로 두고 점수 계산은 화면과 독립적으로 만듭니다. | 콘솔 대신 GUI를 붙일 때 계산기를 그대로 쓸 수 있나요? |
| 알고리즘·자료구조 | vector, 순차 순회, 다음 원소 참조 | 스트라이크는 다음 2투구, 스페어는 다음 1투구를 참조합니다. | 아직 다음 투구가 없을 때 범위 밖 접근을 어떻게 막을까요? |
| 설계 패턴 | 단일 책임·순수 계산 함수 | 입력 검증·저장·계산·출력을 분리합니다. 복잡한 State 계층은 필수가 아닙니다. | 같은 투구 목록으로 계산을 반복하려면 어떤 상태 변경을 피해야 할까요? |
| 운영체제 | 표준 입력·출력과 스트림 오류 | 문자 입력으로 입력 스트림이 실패했을 때 복구하는 법을 익힙니다. 스레드는 필요하지 않습니다. | 음수와 문자 입력은 어떤 검사로 각각 거부할까요? |

## 3. 구현 환경 세팅

환경: **C++ / Windows 콘솔(CMD)**. 이 절은 개인 Fork 복제 후 수행할 설정입니다. 현재 브랜치에는 문서와 `.gitignore`만 있고 소스·프로젝트·Starter Kit는 없습니다. 아래 설정을 마친 뒤 프로젝트와 기능을 구현해야 빌드할 수 있습니다. 사용할 도구의 정확한 버전은 시작 전에 합의합니다.

1. Visual Studio의 **C++를 사용한 데스크톱 개발** 워크로드와 Windows SDK를 설치합니다.
2. Fork 폴더 안에 C++ 콘솔 앱 프로젝트를 만듭니다. 솔루션·프로젝트 파일이 Fork 안에 저장되는지 확인하고 별도 Git 저장소를 중첩 생성하지 않습니다.
3. 프로젝트 속성에서 C++17 이상, 빌드 플랫폼 x64로 설정합니다. 기본 표준 라이브러리 외 외부 패키지는 필요하지 않습니다.
4. 기본 콘솔 프로그램을 빌드·실행한 뒤 주차별 로직을 작성합니다. 실제 사용한 컴파일러·SDK 버전을 프로젝트 설정에 맞춰 확인합니다.

설정 참고: [Visual Studio C++ 개발](https://learn.microsoft.com/en-us/cpp/get-started/?view=msvc-170).

## 4. 기획안과 구현 목표

### 기획 규칙과 범위

- 투구당 0~10핀입니다. 1~9프레임은 최대 2회 투구하되 스트라이크면 다음 프레임으로 넘어갑니다.
- 스트라이크는 다음 2회 투구, 스페어는 다음 1회 투구를 보너스로 더합니다. 보너스 투구가 남은 프레임은 점수 미확정으로 표시해도 됩니다.
- 10프레임은 스트라이크면 2회, 스페어면 1회 추가 투구합니다. 추가 투구는 새 프레임을 만들지 않습니다.
- 10프레임 첫 투구가 스트라이크인 경우 핀을 다시 세웁니다. 둘째도 스트라이크면 다시 세우고, 아니면 셋째는 둘째 투구 후 남은 핀 범위입니다.

**선택 확장:** 프레임별 점수판, 자동화 단위 테스트. 완료 조건에는 포함하지 않습니다.
**이번 범위에서 제외:** 3D 물리, 레인 렌더링, 실제 볼링 조작.

### 구현할 기능

1. 핀 수를 입력받아 유효한 투구 기록을 저장합니다.
2. 10프레임 점수를 계산하고 스트라이크·스페어 보너스를 반영합니다.
3. 마지막 프레임의 추가 투구를 처리하고 게임 종료 후 입력을 거부합니다.
4. 범위를 벗어난 핀 수나 남은 핀보다 큰 투구는 기록에 넣지 않고 다시 입력받습니다.

### 목표 동작 명세

기획에 따른 기대 결과이며 실제 확인 결과가 아닙니다. 구현하면서 직접 확인하면 되고 별도 검증 보고서는 필요하지 않습니다.

| ID | 확인 방법 | 기대 결과 |
|---|---|---|
| B01 | 20회 모두 0핀 | 0점 |
| B02 | 각 프레임 9핀·0핀을 10회 | 90점 |
| B03 | 5핀·5핀을 10프레임, 추가 5핀 | 150점 |
| B04 | 12회 연속 스트라이크 | 300점, 추가 입력 거부 |
| B05 | 새 게임에서 8핀 다음 5핀 | 둘째 입력 거부, 기존 [8] 유지 |
| B06 | 10프레임에서 10핀·7핀 다음 4핀 | 셋째 입력 거부, 0~3핀만 허용 |

## 5. 프로젝트 Fork와 세팅 후 빌드

### Fork와 작업 브랜치

1. 원본 GitHub 저장소를 개인 계정으로 Fork합니다. 실제 원본 주소가 정해지면 아래 URL 자리표시자를 바꿉니다.
2. PowerShell에서 다음 명령을 실행합니다. `<...>` 전체를 실제 URL로 바꾸세요. 이미 복제했다면 clone과 remote add를 반복하지 않습니다.

```powershell
git clone <개인-Fork-URL> game-system-lab
cd game-system-lab
git remote add upstream <원본-저장소-URL>
git fetch upstream
git switch -c work/02 upstream/week/02-bowling
```

`origin`은 개인 Fork, `upstream`은 원본입니다. 원본에서 주차 브랜치를 가져오므로 Fork에 기본 브랜치만 복사되어 있어도 됩니다. 이미 만든 작업 브랜치로 돌아갈 때는 `git switch work/02`을 사용합니다. 다음으로 3절의 환경을 구성하고 4절의 기능을 구현합니다.

### 빌드와 실행

1. 3절에서 생성하거나 가져온 실제 솔루션 파일을 Visual Studio로 엽니다. 프로젝트를 아직 만들지 않았다면 빌드할 대상이 없습니다.
2. 실행할 프로젝트를 시작 프로젝트로 지정하고 **Debug / x64**를 선택한 뒤 **빌드 → 솔루션 빌드**를 실행합니다.
3. **디버깅하지 않고 시작(Ctrl+F5)**으로 실행합니다. 상태를 추적할 때는 F5로 디버깅하고 중단점에서 값을 확인합니다.
4. 출력 경로는 프로젝트 속성의 출력 디렉터리에서 확인합니다. 소스·솔루션·프로젝트 설정을 함께 관리하고 `.vs/`·중간 생성물·실행 파일은 기존 `.gitignore`로 제외합니다.
5. 콘솔에서 4절의 조작·입력을 사용해 목표 동작을 확인합니다. 입력 대기 중 정지한 상태와 비정상 종료를 구분합니다.
