# Game Systems Lab

고전 게임부터 다양한 장르의 공통 시스템을 살펴보며, **게임 전체가 아니라 핵심 시스템을 각자 설계·구현·검증**하는 스터디입니다.


바로 사용할 수 있는 **[운영 템플릿과 예제](study-guide.md)**: 주차 공지, 주제별 범위·검증 예시와 작성 참고 자료를 제공합니다. 모든 양식을 작성할 필요는 없으며, 결과 공유에 필요한 부분만 골라 씁니다.

## Season 1 — 6개 주제 (기본 6주)

|주차|시스템(주제)|핵심 개념|환경|
|-|-|-|-|
|01|**Pong** — 공·패들 충돌과 점수|게임 루프, 좌표·속도, 충돌 판정, 상태 갱신|**C++ / Windows 콘솔(CMD)**, ASCII 렌더러|
|02|**볼링 게임** — 프레임별 점수 계산|규칙 모델링, 상태 전이, 스트라이크·스페어, 경계값 단위 테스트|**C++ / Windows 콘솔(CMD)**|
|03|**레이싱 게임** — 랩·구간 기록|시간 측정, 이벤트 기반 기록, 상태 관리, 유효 랩 판정|**C++ / Windows 콘솔(CMD)**|
|04|**Tetris** — 보드·블록·라인 삭제|2D Grid, 회전·충돌, 게임 상태와 렌더러 분리, 동일 입력 재현|**C++ 코어 + CMD ASCII**, 선택: **DirectX 12 Sprite Renderer**|

## 일정과 운영 원칙

- 각 주제는 **1주 단위 진행을 기본**으로 합니다. 주제 시작 전에 참여자 합의로 **시작일·작업 마감일·발표일**을 정하고 Discord 공지에 기록합니다.
- 난이도와 참여자 일정에 따라 기간을 조정할 수 있습니다. 연장이나 발표 일정 변경이 필요하면 마감 전에 논의하고, 합의한 일정을 Discord 공지에 반영합니다.
- 표의 주차는 주제의 진행 순서입니다. 기간 조정에 따라 시즌 전체 일정은 6주보다 길어질 수 있습니다.
- Tetris의 DX12 포팅 등 확장 과제는 선택 사항입니다. 제공 엔진 설정 시간은 가능한 한 최소화합니다.

## 진행 방법

1. 운영자는 `week/01-pong` 같은 **주차별 브랜치**에 명세, 에셋, 실행 가능한 Starter Kit, 테스트 조건을 공개합니다. `main`은 스터디 안내와 일정만 관리합니다.
2. 참여자는 이 저장소를 **개인 계정으로 Fork**하고, 아래 절차에 따라 해당 주차 브랜치에서 개인 작업 브랜치를 만들어 독립적으로 구현합니다.
3. 작업 중에는 Discord 작업방에서 화면을 공유하며 질문하고 토론할 수 있습니다. 제공 코드와 직접 구현한 영역, 참고한 자료는 결과에 구분해 기록합니다.
4. 합의한 마감일까지 **Fork 저장소의 작업 브랜치 링크와 작업 결과를 Discord에 공유**합니다. 아래의 가벼운 결과 공유 항목만 정리하고, 미완성이라면 현재 진행 상황과 막힌 점을 적습니다.
5. 합의한 발표일에 **실행 시연 → 설계 근거 → 테스트 결과 → 대안과 개선점** 순서로 발표하고, 질의응답과 피드백을 나눕니다. 피드백을 반영해 수정했다면 같은 Discord 게시글에 변경 내용과 링크를 덧붙입니다.

## 발표와 불참 시 진행

- 개인별 **발표 5분 + 질의응답 5분**을 기본으로 합니다. 참여 인원과 주제에 따라 해당 회차 시작 전에 시간을 조정합니다.
- 발표에서는 핵심 구현 하나, 선택한 이유, 검증 결과, 개선할 점을 중심으로 설명합니다. 미완성인 경우에도 시도한 접근과 실패 원인을 공유합니다.
- 발표에 불참할 경우 가능하면 사전에 Discord에 알리고, **발표 시작 전까지 기존 결과 게시글에 핵심 설명이나 짧은 시연을 보완**합니다. 이미 코드·시연·핵심 설명을 공유했다면 별도 대체 발표 자료는 만들지 않아도 됩니다.
- 긴급한 사정으로 기한을 지키기 어려우면 가능한 시점에 상황과 대체 제출 예정일을 공유하고 일정을 조율합니다. 게시글에 달린 질문은 가능한 시간에 답변합니다.

## 완료 기준

- 운영자는 주제 공개 시 **필수 요구사항, 선택 확장, 실행 방법, 검증 시나리오와 기대 결과**를 구분해 명시합니다. 필수 범위는 기본 진행 기간 안에 완성할 수 있도록 정합니다.
- **필수 요구사항 구현 + 핵심 동작 확인 + 가벼운 결과 공유**를 충족하면 해당 주제를 완료한 것으로 봅니다. 검증은 실제 동작을 확인하기 위한 과정이며, 별도 테스트 보고서 제출은 요구하지 않습니다. 선택 확장 여부는 완료 판단에 영향을 주지 않습니다.
- 미완성 결과도 공유와 발표가 가능합니다. 충족하지 못한 항목과 원인, 다음 시도를 기록하며 완료 여부와 구분합니다.
- 검증에는 정상 동작과 경계·예외 상황을 포함합니다. 예를 들어 볼링 점수는 스트라이크·스페어·마지막 프레임을, 랩 기록은 출발 전 통과·체크포인트 누락·재시작을 확인합니다. 핵심 확인 결과는 결과 게시글에 한두 줄로 적으면 됩니다. 자동 테스트나 자세한 재현 기록은 도움이 될 때만 추가합니다.

## 실행 환경과 버전

- 운영자는 Starter Kit의 README에 검증한 **운영체제, 개발 도구·엔진의 정확한 버전, 필요한 패키지, 설치·빌드·실행 절차**를 기록합니다.
- C++ 과제는 컴파일러·도구 집합, C++ 표준, Windows SDK, 빌드 구성(Debug/Release)을 기록합니다. DirectX 12 과제는 GPU·드라이버와 필요한 실행 조건도 안내합니다. Unity 과제는 에디터와 패키지 버전을 프로젝트 설정·패키지 목록에 고정합니다.
- 참여자는 제공 환경을 기본으로 사용하고, 다른 환경을 사용했다면 변경한 버전·설정과 실행 확인 결과를 제출물에 기록합니다. 진행 중 공통 환경 변경은 참여자와 합의한 뒤 공지합니다.

## AI 활용 기준

- AI는 개념 학습, 설계 대안 탐색, 코드 작성·검토, 디버깅에 활용할 수 있습니다. **제출한 구현은 본인이 동작 원리와 설계 이유를 설명하고 수정할 수 있어야 합니다.**
- AI가 제안한 코드·수식·설명은 직접 실행하거나 검증한 뒤 반영합니다. 발표에서는 직접 판단한 내용과 AI의 도움을 받은 부분을 구분합니다.
- AI 도움을 받았다면 핵심 설명에 **도움받은 범위와 직접 확인한 내용**을 한 줄로 덧붙입니다. 별도 AI 활용 보고서나 미사용 선언은 필요하지 않습니다. 전체 대화나 모든 프롬프트 제출은 요구하지 않습니다.
- 참고 코드·에셋·자료의 출처와 사용 조건을 확인하고 기록합니다. 비공개 코드, 개인 정보, 비밀 키는 AI 입력이나 공개 제출물에 포함하지 않습니다.

## Fork와 작업 브랜치 만들기

1. 원본 저장소의 GitHub 페이지에서 **Fork**를 눌러 개인 계정에 복사합니다. Fork 설정의 **Copy the main branch only** 선택을 해제해 주차별 브랜치도 가져옵니다.
2. 개인 Fork를 로컬로 복제하고, 원본 저장소를 `upstream`으로 등록합니다. 아래 주소는 실제 저장소 주소로 바꿉니다. 이 과정은 최초 한 번만 수행합니다.

```sh
git clone <개인-Fork-저장소-URL>
cd <복제된-저장소-폴더>
git remote add upstream <원본-저장소-URL>
```

3. 매 주제 시작 시 원본의 최신 브랜치를 가져오고, 해당 주차 브랜치에서 개인 작업 브랜치를 만듭니다. 아래는 01주차 예시이며, 다음 주차에는 원본 브랜치명과 개인 작업 브랜치명을 바꿉니다.

```sh
git fetch upstream
git switch -c work/01 upstream/week/01-pong
```

4. 구현 결과를 커밋하고 개인 Fork에 올립니다. `git add`에는 공유할 파일만 지정하며, 빌드 결과물·캐시·비밀 키 등은 제외합니다.

```sh
git add <작업한-파일-또는-폴더>
git commit -m "Complete week 01 study"
git push -u origin work/01
```

이미 만든 작업 브랜치에서 작업을 이어갈 때는 `git switch work/01`을 사용합니다. `-c`는 새 브랜치를 만들 때만 사용합니다. `upstream`은 원본 과제를 가져오는 곳, `origin`은 개인 결과를 올리는 곳입니다. 원본 과제가 수정되었다면 운영자의 변경 안내를 확인하고 현재 작업을 커밋한 뒤 반영합니다. 충돌이 나면 해결 전 상태에서 강제 덮어쓰지 말고 작업방에 질문합니다.

5. GitHub에서 개인 Fork의 `work/01` 브랜치를 열어 링크를 복사하고 Discord에 공유합니다. 제출은 이 링크 공유로 진행합니다.

## 가벼운 결과 공유

포트폴리오에 다시 활용할 수 있는 **코드·실행 방법, 짧은 시연, 핵심 설명**만 공유합니다. 개인 Fork의 README 하나에 모으고 Discord에는 링크만 올려도 됩니다. 별도 보고서·발표 슬라이드·회고 문서는 필수가 아닙니다.

```text
[주차 / 주제] 이름
- 코드·실행 방법: <Fork 브랜치 링크; 필요한 환경과 실행 순서를 README에 안내>
- 시연: <스크린샷·짧은 영상 또는 콘솔 결과>
- 핵심 설명: <구현한 기능 / 핵심 선택과 이유 / 확인한 동작·남은 한계, 총 3~5줄>
```

예: “점수 계산과 투구 입력을 분리해 같은 입력으로 계산기를 확인할 수 있게 했습니다. 스트라이크 300점·스페어 150점을 확인했습니다. 잘못된 입력 처리는 아직 보완 중입니다.”

외부 코드·에셋을 가져왔다면 출처와 사용 조건을, AI 도움을 받았다면 도움받은 범위와 직접 확인한 내용을 필요한 만큼 덧붙입니다. 미완성 작업도 현재 결과와 막힌 점을 공유하면 됩니다.

## 선택 자료

단위 테스트, 상세 설계 노트, 검증 표, 회고, 발표 슬라이드 등은 **본인 학습이나 포트폴리오 설명에 도움이 될 때만** 추가합니다. [운영 템플릿과 작성 예시](study-guide.md)는 필요한 부분을 골라 쓰는 참고 자료이며, 모두 작성하는 체크리스트가 아닙니다.

**범위 원칙:** 필수 요구사항을 먼저 완성합니다. 선택 기능은 별도 도전 과제로 두며, 전체 게임 클론으로 확대하지 않습니다.
