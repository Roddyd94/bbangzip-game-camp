# 빵집 게임 프로그래밍 캠프

Unreal로 프로젝트를 만들어 본 참여자들이 게임의 핵심 시스템을 직접 설계·구현하는 스터디입니다. 엔진에서 사용했던 World·Object·Component·Tick의 역할을 돌아보고, 이동·충돌·규칙·상태 관리가 실제로 어떻게 동작하는지 구현으로 확인합니다.

주제는 1주 단위로 진행하되 **시작일·작업 마감일·발표일은 참여자 합의로 정합니다.** 주어진 기반 위에서 핵심 시스템에 집중하며, 결과는 개인 Fork에 올리고 Discord에서 공유·발표합니다.

## 먼저 시작하기

현재 공개된 과제는 [01주차 Pong](https://github.com/Roddyd94/bbangzip-game-camp/tree/week/01-pong)입니다. 창·입력·렌더링·파일 로딩은 제공되며 실행하면 정지한 패들·공·중앙선이 표시됩니다. 참여자는 MovementComponent부터 이동·충돌·득점·리스폰을 완성합니다.

- 과제 명세·사전 지식·구현 목표·빌드 방법: **주차 브랜치의 readme.md**
- 일정·결과 공유·발표를 위한 복사 양식과 작성 예시: [study-guide.md](study-guide.md)
- C++ 작성 규칙: [convention/sfml.md](convention/sfml.md)
- Unity 작성 규칙: [convention/unity.md](convention/unity.md)

main은 공통 안내·운영 가이드·컨벤션 원본을 관리합니다. 실행할 프로젝트는 해당 주차 브랜치에서 받습니다.

## 주제와 환경

다른 게임에도 공통인 시스템은 장르명으로 표기합니다. 현재 과제명으로 사용하는 Pong·Tetris·Space Invaders는 주제를 식별하기 위한 명칭입니다. 구현에는 제공 도형과 허용된 자료를 사용합니다.

|---|---|---|---|
| 01 | Pong — 공·패들 충돌과 점수 | 벡터·시간 기반 이동, 선분 충돌, 반사, 상태 전환 | **Windows x64 / MSVC / C++17 / SFML 3.1.0**, 실행 기반 제공·핵심 구현 TODO |
| 02 | 볼링 게임 — 프레임별 점수 계산 | 규칙 모델링, 스트라이크·스페어, 마지막 프레임 | **Unity / C#**, 플레이 장면·물리·입력을 제공하는 구성 예정 |
| 03 | 레이싱 게임 — 랩·구간 기록 | 이벤트 순서, 시간차, 체크포인트, 유효 랩 | **Unity / C#**, 차량·트랙·통과 이벤트를 제공하는 구성 예정 |

## 01주차에서 제공하는 것과 구현하는 것

Unreal 프로젝트 경험은 전제로 하되 SFML 사용 경험은 요구하지 않습니다. SFML 창이나 렌더러를 다시 만드는 대신, 제공 코드의 진입점과 수명·갱신 순서를 확인합니다.

| 구분 | 범위 |
|---|---|
| 제공 기반 | main의 엔진 초기화·실행 호출, Subsystem, World와 객체 ID·활성 플래그·지연 삭제, Tick → Collision → Render 루프 |
| 제공 입출력 | InputComponent, TimeManager의 초 단위 deltaTime, FileSerializer, ini·world 데이터, 셰이프 표시 |
| 제공 객체 구조 | 인터페이스 기본 구현과 World 참조를 갖는 GameObject, 공통 데이터·직렬화의 PongBody, World가 소유하는 PongGameRule |
| 제공 수학 도구 | utility의 clamp·lerp·inverseLerp·각도 변환·벡터 계산 |
| 직접 구현 | MovementComponent의 데이터·API·연산 설계, Paddle·Ball의 이동 컴포넌트 초기화, 이동·경계 제한·충돌 반응·가속·득점·대기·리스폰·전체 Reset |

PongGameRule에는 경계·점수·리스폰 대기 시간이 있고, Ball과 Paddle은 자신이 속한 World를 통해 규칙을 조회합니다. world 행의 첫 토큰이 생성 클래스를 선택하며 별도 PongKind는 사용하지 않습니다. Paddle에는 플레이어 번호 1·2를 저장합니다.

MovementComponent는 클래스 골격만 제공합니다. 속력·방향·변위 계산에 필요한 멤버와 함수를 직접 설계합니다. `utility` 사용은 선택이며 편의 함수가 이동·충돌 문제의 구현을 대신하지 않습니다.

필수 목표에는 빠른 공의 패들 관통을 방지하는 선분 판정, 접촉 위치에 따른 45~135도 로컬 반사각, 명중당 가속, 득점 후 3초 대기와 중심선 리스폰이 포함됩니다. 정확한 규칙은 주차 README를 기준으로 합니다. 한 프레임의 벽·패들·득점 처리 순서도 검토하고, 여러 연속 충돌의 남은 시간 처리 수준은 회차 시작 시 합의합니다.

## 일정과 진행

1. 운영자가 실행 가능한 기반과 주차 README를 공개합니다. README는 **주제 → 사전 지식 → 구현 환경·목표 → Fork·빌드 방법** 순서로 구성하고 제공 범위와 구현 대상은 표로 구분합니다.
2. 참여자들이 시작·마감·발표 시각을 합의하고 Discord 공지에 남깁니다. 기본 작업 단위는 1주이며, 변경할 때는 마감 전에 논의하고 원래 공지를 갱신합니다.
3. 개인 Fork의 작업 브랜치에서 구현합니다. 수학·물리·컴퓨터 과학·엔진 원리의 사전 지식은 개인적으로 학습하며 학습 노트는 제출하지 않습니다.
4. 합의한 마감일까지 코드·실행 안내, 짧은 시연, 핵심 설명을 Discord에 공유합니다. 개인 README에 모으고 게시글에는 링크만 연결해도 됩니다.
5. 발표는 **시연 → 핵심 설계와 선택 이유 → 확인한 동작·한계** 순서로 진행합니다. 기본은 발표 5분·질의응답 5분이며 인원에 따라 조정합니다.

미완성도 공유·발표합니다. 동작하는 범위와 남은 문제를 설명하면 됩니다. 불참 시 사전에 알리고 기존 결과 게시글로 발표를 대체할 수 있습니다. 별도 슬라이드·보고서·대체 발표 영상은 요구하지 않습니다. 질문과 수정 내용은 같은 게시글에 이어 남깁니다.

## Fork와 01주차 시작

[원본 저장소](https://github.com/Roddyd94/bbangzip-game-camp)를 개인 계정으로 Fork합니다. 아래 `<개인-Fork-URL>`은 본인 Fork의 복제 주소로 바꿉니다. `origin`은 결과를 올리는 개인 저장소, `upstream`은 과제를 받는 원본입니다. main만 Fork했어도 upstream에서 주차 브랜치를 가져올 수 있습니다.

```powershell
git clone <개인-Fork-URL> bbangzip-game-camp
cd bbangzip-game-camp
git remote add upstream https://github.com/Roddyd94/bbangzip-game-camp.git
git fetch upstream
git switch -c work/01 upstream/week/01-pong
.\build.ps1
.\build\result\StudyGame.exe
```

Windows에서 Visual Studio의 C++ 데스크톱 개발·Windows SDK·CMake 도구가 필요합니다. SFML 의존성은 과제에 포함됩니다. 빌드 스크립트는 src/todo의 cpp를 자동으로 수집하고 core·main과 함께 빌드하며, `build/result/`에 실행 파일·DLL·content를 배치합니다. 정지 화면이 표시되면 제공 기반이 실행된 것입니다.

이미 복제했다면 clone·remote add를 반복하지 않습니다. 작업 브랜치를 이미 만들었다면 `git switch work/01`로 돌아옵니다. 변경한 코드와 설명을 개인 Fork에 올립니다.

```powershell
git add src/todo readme.md
# content를 수정했다면 해당 설정 파일도 추가합니다.
git commit -m "Implement Pong movement and collision"
git push -u origin work/01
```

빌드 출력은 커밋하지 않습니다. 실행 파일을 공유할 때는 DLL·content가 포함된 `build/result` 전체를 묶습니다. 공통 기반은 필요한 경우 수정할 수 있으며, 변경 이유를 핵심 설명에 남깁니다. 원본 과제 업데이트는 작업을 커밋한 뒤 운영자의 안내에 따라 반영합니다.

## 공유·완료 기준

**코드와 실행 방법, 짧은 시연, 핵심 설명 3~5줄**이면 충분합니다. 시연에는 대표 동작과 경계 상황 하나를 담고, 설명에는 직접 구현한 범위·선택한 이유·확인 결과·남은 한계를 적습니다. 필수 동작을 구현하고 확인한 뒤 결과를 공유하면 완료로 봅니다. 추가 테스트·설계 문서·슬라이드는 포트폴리오에 도움이 될 때만 만듭니다.

빈 템플릿과 채운 예시는 [운영 가이드](study-guide.md)에 있습니다. 제공 코드의 기능을 본인 구현으로 설명하지 않고, 참고 코드·에셋의 출처와 필요한 사용 조건을 함께 남깁니다.

AI는 학습·설계·구현·검토에 활용할 수 있습니다. 본인이 설명하고 수정할 수 있는 코드만 반영하고, 도움받은 범위와 직접 확인한 내용을 한 줄로 적습니다. 전체 프롬프트나 별도 AI 보고서는 제출하지 않습니다.
